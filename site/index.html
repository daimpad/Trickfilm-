Trickfilm-Werkstatt

Eine Werkstatt für Trickfilme mit Figuren, Vertonung und Geräuschen. Diese Seite erklärt, was die Werkstatt kann und wie man sie bedient. Jeder Abschnitt beginnt mit dem Wesentlichen; technische Einzelheiten stehen aufklappbar darunter.

Stand: {{ERSTELLT}} · Quelle: github.com/daimpad/trickfilm

Überblick

Die Werkstatt baut kurze Trickfilm-Szenen, wie man sie aus Lern- und Erklärvideos kennt: Menschen am Schreibtisch, am Schalter, unterwegs, dazu Geräte, Papiere und Zeichen. Sie ist unabhängig von einem bestimmten Auftrag. Inhalte, Sprechtexte und das Erscheinungsbild eines Auftraggebers kommen später als Eingaben dazu.

Vier Ideen tragen alles:

  • Jedes Bild wird gerechnet. Zu jedem Zeitpunkt einer Szene ergibt sich das Bild aus einer Rechenvorschrift. Gleiche Eingabe ergibt immer dasselbe Bild.
  • Figuren sind Gliederpuppen. Ein festes Skelett (Rig) trägt austauschbare Zeichnungen (Teilesätze). So lassen sich verschiedene Menschen mit denselben Bewegungen zeigen.
  • Geräusche entstehen aus der Bewegung. Wo eine Hand auf die Tastatur trifft, entsteht ein Anschlag, nicht dort, wo jemand ihn von Hand hinsetzt. (Die Werkzeuge stehen; die Klänge werden nach Kostenfreigabe generiert.)
  • Was am Bild zu sehen ist, wird am Bild geprüft. Zu jeder Szene gibt es Standbilder, die ein Mensch ansieht, und Prüfungen, die eine Maschine über jedes einzelne Bild fährt.
Technische Einzelheiten

Die Bibliothek unter lib/ ist reines JavaScript ohne Zugriff auf eine Webseite (DOM-frei). Sie läuft unverändert in drei Umgebungen: im Browser-Prototyp, in Node (Prüfungen, Standbilder) und in Remotion (fertiges Video). Eine Szene besteht aus vier Dateien: brief.yaml (Szenenbrief), geometry.js (Positionen und Palette), scene.js (Aufbau aus Figuren und Requisiten) und animation.js (die Zeitfunktion computeState(t)).

Format: 1920 × 1080 Pixel, 30 Bilder je Sekunde. Werkzeuge in TypeScript, Bibliothek in JavaScript, Render mit Remotion 4, Standbilder und Tests mit Chromium über Playwright.

Grundsätze

Zehn Regeln gelten überall. Sie sorgen dafür, dass Szenen wiederholbar, prüfbar und unabhängig von einzelnen Rechnern bleiben.

  1. Jedes Bild ist eine Funktion der Zeit. Keine Animation läuft „von selbst“; Zufall gibt es nur mit festem Startwert.
  2. Die Bibliothek ist unabhängig vom Browser. Dieselbe Rechnung läuft im Prototyp, in Prüfungen und im Video.
  3. Geometrie ist Daten. Positionen, Maße und Farben stehen in eigenen Dateien, nie verstreut im Bildaufbau.
  4. Bild und Ton werden nicht beide geraten. Mit Aufnahme folgen die Bewegungen den gemessenen Wortzeiten; ohne Aufnahme wird die Dauer geschätzt (15 Zeichen je Sekunde plus 10–15 % Luft) und als Schätzung markiert.
  5. Geräusche entstehen aus der Bewegung.
  6. Was gerechnet ist, wird nie von Hand gepflegt. Erzeugte Dateien tragen den Vermerk „ERZEUGT von …“ und werden immer neu erzeugt, nie nachgebessert.
  7. Was am Bild zu prüfen ist, wird am Bild geprüft.
  8. Ein Lauf, der etwas nicht weiß, sagt es. Kein Werkzeug liefert ein leeres Ergebnis, das wie „nichts zu tun“ aussieht.
  9. Kein Netz beim Rendern. Alles, was generiert wird, liegt vorher im Repository.
  10. Keine Geheimnisse im Repository. Zugangsschlüssel kommen nur aus der Umgebung.
Technische Einzelheiten

Verboten sind CSS-Animationen, SMIL, transition, requestAnimationFrame als Zeitgeber, GSAP und Framer Motion. Zufall läuft über den Generator prng(seed) aus lib/zufall.js. Die Verbotsprüfung (npm run verboten) sucht im Repository nach Verstößen, zum Beispiel Math.random, Date.now und Farbwerte außerhalb der Tokens im Bildcode, Webfonts, Netzaufrufe und Zugangsschlüssel.

Der Weg einer Szene

Jede Szene entsteht in elf Schritten. Die Befehle laufen in einem Terminal im Ordner des Repositorys.

  1. Anlegen: npm run szene:neu -- FILM-01-name kopiert die Vorlage.
  2. Szenenbrief schreiben (brief.yaml): der Sprechtext wörtlich, These und Pointe in je einem Satz, Figuren mit Charakter, die Abschnitte (Beats) mit Zeiten, Beschriftungen und eine Beschreibung des Bildes für Menschen, die es nicht sehen.
  3. Geometrie festlegen (geometry.js): wo Figuren und Dinge stehen, wohin Hände greifen.
  4. Szene aufbauen (scene.js): Figuren und Requisiten in einer begründeten Reihenfolge von hinten nach vorn.
  5. Bewegung schreiben (animation.js): was zu jedem Zeitpunkt geschieht. Posen lassen sich im Posen-Editor setzen.
  6. Geräusche zuordnen (im Szenenbrief unter sfx): welche Ereignisse klingen, zum Beispiel jeder dritte Tastenanschlag. npm run sfx:cues -- FILM-01-name --stichprobe findet die Zeitpunkte in der Bewegung. Siehe Geräusche.
  7. Bauen: npm run szene:bauen -- FILM-01-name prüft die Szene und erzeugt den Prototyp.
  8. Ansehen: npm run szene:kontaktbogen -- FILM-01-name erzeugt neun Standbilder. Jedes wird angesehen: Liegt etwas falsch vor dem Körper? Greift ein Arm durch einen Tisch? Ist die Pointe auch klein lesbar?
  9. Prototyp öffnen und abspielen.
  10. Protokoll schreiben: npm run szene:protokoll -- FILM-01-name.
  11. Anhalten und den Stand in wenigen Zeilen melden.

sichtung: { lesbarkeit_960: offen, synchron: offen }

Der Brief wird von einem eigenen Leser für eine Teilmenge von YAML gelesen; was nicht hineinpasst, meldet er mit Zeilennummer.

Technische Einzelheiten: was der Build prüft
  • Brief und Code stimmen überein: Dauer, Abschnitte mit Namen und Zeiten, Palette (nur Farben der Tokens), Beschriftungen, Textäquivalent, Figuren mit Rig und Teilesatz.
  • Das Bild enthält keine Animationen, Verläufe, Filter, Masken oder abgerundeten Ecken.
  • Für jedes einzelne Bild der Szene: jede bewegte ID existiert, jedes Attribut ist vorhanden, kein Wert ist ungültig (NaN).
  • Jede Hand erreicht ihr Ziel; sonst nennt der Build Bild, Arm und Abstand.
  • Kein Text reicht in die Schutzzone für Untertitel; jede Beschriftung steht lange genug, um sie zu lesen.
  • Gleiche Zeit ergibt denselben Zustand (Wiederholbarkeit).

Das Ergebnis ist szenen/<ID>/dist/index.html, eine einzige Datei, die nichts nachlädt. Die Bibliothek ist darin über eine Import-Map eingebettet; jedes Modul bleibt ein echtes JavaScript-Modul.

Figuren

Eine Figur setzt sich aus vier Dingen zusammen: einem Archetyp (dem Skelett), einem Teilesatz (den Zeichnungen), einer Palette (Farben der Kleidung) und einer Blickrichtung. Figuren haben keine Gesichter; Gefühle zeigen sich in Haltung, Tempo und Pausen.

ArchetypWofürBewegliche Teile
sitzend-profilSchreibtisch, Schalter, GesprächRumpf, Kopf, zwei Arme mit Händen; Beine sitzend, Fuß kann wippen
stehend-profilGehen, Warten, Tragendazu zwei Beine mit Füßen und Gang
stehend-frontalZeigen, Erklären, ReagierenArme seitlich, Schultern heben, Haltung „vor dem Körper halten“
oberkoerper-nahReaktion, Dialog, PointeOberkörper in größerem Maßstab

Einen eigenen Teilesatz zeichnen

  1. Die Zeichenvorlage figuren/vorlage_<archetyp>.svg nach figuren/teilesaetze/satz-01/<archetyp>.svg kopieren.
  2. In Illustrator oder Inkscape jedes Teil in die Ebene mit genau seinem Namen zeichnen (torso, head, armF-upper …). Die blassen Formen und blauen Kreise sind Hilfen und dürfen bleiben.
  3. Jedes Teil deckt den blauen Kreis an seinen Gelenken, sonst entstehen beim Drehen Lücken.
  4. Kleidung in den Schlüsselfarben zeichnen: Magenta für Kleidung 1, Gelb für Kleidung 2, Grün für Zubehör. Diese Flächen färbt jede Szene um; alle anderen Farben bleiben, wie gezeichnet.
  5. Als SVG exportieren und einlesen: npm run figuren:import -- satz-01.

Einfacher geht es mit der Teile-Werkstatt: jedes Teil als eigene Datei zeichnen, laden und einpassen.

Technische Einzelheiten: Rig und Importer

Die Maße stehen in figuren/rig-spezifikation.json (Oberarm und Unterarm je 90 px, Schulter 130 px über der Hüfte, Boden bei y 760, Tischplatte bei y 560). Der Zustand einer Figur steht im Figurenrahmen: Blick nach rechts, Winkel vorwärts positiv, Arme absolut, Kopf relativ zum Rumpf. Die Spiegelung für den Blick nach links übernimmt das Rig selbst.

Der Importer prüft die Zeichnung (alle Teile vorhanden, keine fremden Ebenen, keine Transformationen, nur erlaubte Formen, Farben und Konturen von 4 oder 6 px), verschiebt jedes Teil um seinen Drehpunkt und dreht jedes Gelenk in Chromium auf −60°, 0°, +60° und +120°. Bleibt dabei im Überlappungskreis eine Lücke, meldet er sie. Er ändert keine Zeichnung; Befunde stehen in figuren/import.tsv.

Exportregeln: SVG mit Präsentationsattributen (kein style, keine Klassen), Ebenennamen als IDs, zwei Nachkommastellen; keine Verläufe, Filter, Masken, Schatten, Deckkraft, Texte oder Bilder.

Bewegung und Spielweise

Bewegung entsteht aus wenigen Bausteinen:

  • Kurven geben einer Bewegung ihren Charakter: weich, mit Anlauf, mit Überschwingen, mit Nachschwingen oder von Pose zu Pose.
  • Handziele: Arme werden über den Punkt gesteuert, an dem die Hand sein soll. Die Werkstatt rechnet die Gelenkwinkel selbst aus und meldet, wenn ein Ziel zu weit weg ist.
  • Gang: ein Doppelschritt auf etwa 140 px Strecke; der tiefste Fuß steht immer auf dem Boden, das Knie zeigt immer nach vorn.
  • Spielweise: Gefühle wie konzentriert, genervt, überrascht, erleichtert, stolz oder ratlos sind fertige Rezepte für Haltung und Tempo, die sich addieren lassen.
  • Charakter: Je Figur bestimmen Tempo, Grundhaltung, Stärke der Reaktion und eine kleine Eigenheit (zum Beispiel Fußwippen), wie sie sich bewegt.

Der Witz liegt immer in der Situation, nie in der Person. Eine Pointe ist ein eigener Abschnitt und folgt auf einen Anlauf.

Posen-Editor

Der Posen-Editor macht das Stellen einer Figur anschaulich. Man zieht an Griffen direkt auf der Bühne: dunkel an der Hüfte, weiß an Rumpf und Kopf, farbig an Händen und Füßen. Eine gezogene Hand folgt ihrem Ziel; ein Ring zeigt die Reichweite und wird rot, wenn das Ziel zu weit weg liegt. Regler erlauben genaue Werte, die Pfeiltasten verschieben den gewählten Griff um 1 px, mit Umschalt um 8 px.

Mehrere Posen lassen sich als Schlüsselposen auf einer Zeitleiste setzen und in einer Vorschau abspielen. Der Editor schreibt daraus Code, der in die Szene kopiert wird.

Teile-Werkstatt

Die Teile-Werkstatt vereinfacht das Zeichnen einer neuen Figur. Statt eine ganze Zeichenvorlage mit allen Ebenen auszufüllen, zeichnet man jedes Körperteil für sich, in einem beliebigen Programm und Maßstab, und lädt es als SVG-Datei. Heißt die Datei nach dem Teil, etwa kopf.svg, oberarm.svg, hand.svg oder fuss.svg, findet die Werkstatt ihren Platz selbst.

  • Einpassen: Die Werkstatt legt die Längsachse des Teils auf das Skelett. Korrigiert wird durch Ziehen am Teil (verschieben) und am roten Griff (drehen und skalieren um das Gelenk) oder über Zahlenfelder.
  • Ableiten: Fehlen hintere oder rechte Glieder, werden sie aus den vorhandenen gewonnen, frontal gespiegelt. Fehlende Handformen entstehen aus der offenen Hand. Was dann noch fehlt, ergänzt auf Wunsch der Platzhalter satz-00.
  • Prüfen: Sechs Testposen zeigen die Figur sofort in Bewegung. Jedes Gelenk wird bei −60°, 0°, 60° und 120° auf Lücken geprüft; eine Lücke erscheint rot an Teil und Gelenk.
  • Farben: Flächen, die je Szene umgefärbt werden sollen (Kleidung, Zubehör), werden per Auswahl zugeordnet. Alle anderen Farben bleiben, wie gezeichnet.
  • Ausgabe: Ein Satz Einzelteile ergibt alle drei Profilfiguren (sitzend, stehend, nah). Das ZIP-Archiv enthält sie im Austauschformat und eine Anleitung zum Einlesen.

Aufruf im Repository: npm run teile, Ergebnis unter out/teile/teile-werkstatt.html. Das heruntergeladene Archiv wird unter figuren/teilesaetze/ entpackt und mit npm run figuren:import -- satz-01 eingelesen; der Importer prüft dieselben Regeln noch einmal.

Geräusche

Geräusche sind dezent und eher zum Schmunzeln: eine etwas zu eifrige Tastatur, ein Drucker, der kurz nachdenkt. Ausgeschlossen sind Boing, Fanfare, Lachen, Applaus, Explosionen und Musik. Je Szene klingen drei bis sechs Geräuscharten, höchstens sechs Geräusche in einer Sekunde und höchstens ein kurzer Laut wie „oh?“.

Die Zeitpunkte werden nicht von Hand gesetzt. Die Werkstatt spielt die Bewegung Bild für Bild ab und erkennt, wo etwas anschlägt, losgeht, ankommt oder erscheint. Der Szenenbrief sagt nur, welche dieser Ereignisse klingen und welches Geräusch aus dem Katalog dazugehört.

  1. Katalog: rund 40 Geräusche und drei Laute mit Beschreibung, Länge und Pegel (lib/sfx/katalog.yaml).
  2. Kostenfreigabe: npm run sfx:kosten listet, was generiert werden müsste, und schätzt die Credits. Generiert wird erst nach Zustimmung der Regie.
  3. Hörprobe: npm run sfx:hoerprobe zeigt alle Varianten mit Messwerten zum Anhören und Auswählen.
  4. Bearbeiten: npm run sfx:normalisieren schneidet Stille ab, kürzt auf genau einen Anschlag, blendet weich und bringt alles auf denselben Pegel.
  5. Zuordnen: npm run sfx:cues -- <Szene> --stichprobe schreibt die Liste der Geräusche und zeigt je Ereignis das Bild davor, darauf und danach.
Technische Einzelheiten

Erkennungsarten in lib/events.js: Tiefpunkt (Anschlag, Stempel), Beginn (Klick), Nulldurchgang (Schritt), Bewegungsbeginn und -ende (Abheben, Ankunft), Aufprall, Hüllkurve (Gerät) und Schwelle (Erscheinen). Pfade zeigen in den Zustand oder in die Gelenke einer Figur, etwa A.armF.hand.y. Aus einem Vorrat wählt ein Hash über Szene, Typ und laufende Nummer die Variante, nie zweimal dieselbe hintereinander.

Pegel: −20 LUFS größte Momentanlautheit, True Peak höchstens −3 dBTP, gemessen nach ITU-R BS.1770 in lib/sfx/lautheit.js und mit ffmpeg gegengeprüft. Ausgabe als WAV mono 48 kHz 24 bit und als OGG/Opus für den Prototyp. Im Prototyp liegt der lauteste Cue bei 0 dB, die übrigen relativ dazu.

Requisiten

Möbel, Geräte, Büromaterial, Dinge im Freien und Zeichen stehen als fertige Bausteine bereit. Sie sind aus Flächen mit Kontur gebaut, ohne Schatten und Verläufe. Bewegliche Teile wie eine Schublade, das Papierfach eines Druckers oder der Hörer eines Telefons lassen sich einzeln bewegen.

Technische Einzelheiten

Jede Requisite bietet markup(id, pos, farben, opts), ids(id) (bewegliche Gruppen), anker(pos) (benannte Punkte, etwa die Tasten einer Tastatur als Handziel) und rahmen(). Braucht eine Szene etwas, das fehlt, baut sie es in ihrer eigenen requisiten.js; braucht es eine zweite Szene, wandert es in die Bibliothek.

Gestaltung

  • Bühne 1920 × 1080; die Grafik steht im Bereich x 128–1792, y 96–816, Beschriftungen in festen Plätzen darunter.
  • Schutzzone: Die unteren 140 px bleiben frei von Text und wichtiger Bildaussage, damit Untertitel nichts verdecken.
  • Abstände auf einem 8-px-Raster: 8, 16, 24, 32, 48, 64, 96, 128.
  • Farben nur aus der Palette; je Szene eine helle Grundfläche, eine Akzentfarbe, höchstens eine zweite. Farbe nie allein: Jede Unterscheidung trägt zusätzlich eine Form oder ein Wort.
  • Kontraste werden gerechnet: Text mindestens 4,5:1, Grafik mindestens 3:1.
  • Lesetakt: Jeder Text steht so lange, dass man ihn lesen kann.
  • Keine Dekoration: keine Schatten, Verläufe, Emojis oder abgerundeten Ecken; runde Linienenden nur an Figuren und Zeichen.
  • Schrift: Arial (in der Cloud Liberation Sans mit gleichen Maßen), nie Webfonts.

Prüfungen

Bei jeder Änderung prüft GitHub die ganze Werkstatt automatisch. Erst wenn alles grün ist, wird eine Änderung übernommen. Örtlich läuft dasselbe mit npm run pruefen.

  • Typen und Bibliothekstests (Kurven, Bewegung, Rigs, Requisiten, Briefleser, Build, Prototyp im Browser, Posen-Editor, Importer, Teile-Werkstatt, Geräusche mit Lautheit gegen ffmpeg)
  • Verbotsprüfung: Zugangsschlüssel, unerlaubte Animationen, Zufall ohne Startwert, Farben außerhalb der Palette, Abstände außerhalb des Rasters, Webfonts, Netzaufrufe
  • jede Szene bauen und über jedes Bild prüfen
  • erzeugte Dateien vergleichen: Spezifikation, Vorlagen, Teilesätze mit Gelenkprüfung, Protokolle
Technische Einzelheiten

Der Prüflauf steht in .github/workflows/pruefung.yml, die Verbotsprüfung in tools/pruefen-verboten.ts. Der Prototyp wird in Chromium mit zwei Regeln für automatischen Ton getestet: Erlaubt der Browser Ton, startet die Szene; verlangt er einen Klick, wartet sie bei 0. Ein Test baut absichtlich gestörte Kopien der Vorlage und belegt, dass der Build Fehler tatsächlich meldet.

Zusammenarbeit

Inhaltliche und gestalterische Entscheidungen trifft die Regie. Wo sie zu entscheiden hat, bekommt sie zwei bis vier Möglichkeiten mit einer Empfehlung. Ohne Rückfrage geschieht nicht:

  • eine neue Abhängigkeit aufnehmen;
  • Farben, Maße oder Schrift der Palette ändern;
  • die Rig-Spezifikation ändern (nach ihrer Freigabe);
  • Sprech- oder Bildschirmtext umformulieren;
  • etwas generieren, das Kosten verursacht;
  • eine Seite öffentlich machen.

Solange das Repository öffentlich ist, enthält es keine Kundeninhalte, kein Erscheinungsbild eines Auftrags, keine personenbezogenen Daten und keine unveröffentlichten Sprechtexte.

Die Regeln stehen in CLAUDE.md, ihre Geschichte in docs/CHRONIK.md, Entscheidungen in docs/ENTSCHEIDUNGEN.md. Jede Änderung läuft auf einem eigenen Zweig mit Pull Request gegen main. Renderergebnisse liegen nie im Repository.

Begriffe

ArchetypSkelett einer Figur mit festen Maßen, zum Beispiel sitzend im Profil.
BeatAbschnitt einer Szene mit Anfang, Ende und einer Handlung.
CueEin Geräusch aus dem Katalog, das an einer Stelle klingt.
HandzielDer Punkt, an dem eine Hand sein soll; die Gelenkwinkel rechnet die Werkstatt.
KontaktbogenNeun Standbilder einer Szene auf einem Bild, zum Ansehen und Prüfen.
PointeDer Moment, über den man schmunzelt; er liegt im Ablauf, nie in der Person.
PrototypDie Szene als Webseite zum Abspielen, Anhalten und Springen.
RegieDie Person, die das Repository führt und inhaltlich entscheidet.
RigGliederpuppe einer Figur: Gelenke, Längen und die Rechnung, die Winkel in ein Bild übersetzt.
SchlüsselposeEine festgelegte Pose zu einem Zeitpunkt; dazwischen wird weich verbunden.
SchutzzoneDie unteren 140 px des Bildes, frei für Untertitel.
TeilesatzDie Zeichnungen aller Teile einer Figur, zum Beispiel satz-01.
TokensDie eine Datei mit allen Farben, Strichstärken und Maßen.
